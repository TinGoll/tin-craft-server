- Пользователь: `tincraft-admin`.
- Права: полный `sudo` без пароля (`sudo -n`), правило в `/etc/sudoers.d/tincraft-admin`.

- Публичный ключ: тот же путь с суффиксом `.pub`.
- Отпечаток пользовательского ключа (не ключа сервера): `SHA256:4YCfQ5hd/e86f6w8auRA4k2wCMDBsn+RGWEGejUlu8w`.

Подключение из PowerShell:

```powershell
ssh.exe -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 -i "C:\Users\romao\.ssh\tincraft_vds_ed25519" tincraft-admin@80.64.24.253
```

Проверка доступа:

```powershell
ssh.exe -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 -i "C:\Users\romao\.ssh\tincraft_vds_ed25519" tincraft-admin@80.64.24.253 "id; sudo -n id"
```

Ключ хранится только на этом компьютере. Этот файл документирует существующий доступ, но не предоставляет его на другом компьютере. Если ключ отсутствует или SSH отклоняет подключение, сообщить пользователю; не запрашивать приватный ключ или пароль в чате. Не отключать проверку ключа сервера при ошибке `known_hosts`.

Не выводить приватные ключи, пароли, содержимое `.env` и другие секреты в ответы или журналы. Не копировать их в репозиторий и не коммитить. Полные права использовать только в рамках задачи пользователя; перед изменениями сохранять резервные копии, избегать несогласованных разрушительных действий.

## Развёртывание

Состояние на 26 августа 2026 года; перед изменениями проверять актуальную конфигурацию.

- ОС VDS: Ubuntu 24.04.4 LTS.
- Сайт: `https://tincraft.ru/` и `https://www.tincraft.ru/`.
- Контейнер `nginx_server` (`nginx:stable`) обслуживает HTTP/HTTPS.
- Каталог сайта на VDS: `/app/site`, подключён в nginx как `/var/www/html`.
- Конфигурация nginx: `/app/nginx/conf.d`, основной файл `default.conf`.
- Сертификаты: `/app/certs`, подключены как `/etc/letsencrypt`; приватные ключи не читать и не выводить без необходимости.
- Backend: контейнер `nest_server` (`node:20-alpine`), порт `3000` внутри Docker. nginx проксирует запросы на `http://nest:3000`.
- PostgreSQL: контейнер `tincraft-db` (`postgres:15-alpine`).
- Не предполагать, что локальный `docker-compose.yml` точно соответствует действующему развёртыванию.

Диагностика на сервере:

```bash
sudo -n docker ps
sudo -n docker exec nginx_server nginx -t
sudo -n docker logs --since 10m --tail 100 nginx_server
```

При передаче многострочного PowerShell here-string через SSH учитывать CRLF. Проверенный вариант: передать текст на стандартный ввод SSH с удалённой командой `tr -d '\r' | bash -se`. Содержимое скрипта предварительно проверить; использовать буквальный here-string `@' ... '@`, чтобы PowerShell не подставлял переменные shell.

### Дополнительное исправление кэширования

Пользователь подтвердил, что в обычной вкладке оставалась ошибка, а в инкогнито сайт работал. Одной смены URL скрипта было недостаточно для уже закэшированного HTML.

- В `/app/nginx/conf.d/default.conf` добавлена политика `Cache-Control: no-cache` для `/`, `/index.html` и `/script.js` (включая запросы с версией). Остальные статические ресурсы сохраняют прежнее поведение кэширования.
- Для точного пути `/launcher/version` добавлены `Cache-Control: no-store`, `Vary: Origin` и CORS только для `https://tincraft.ru` и `https://www.tincraft.ru`. Это поддерживает старые закэшированные скрипты с абсолютным URL API. Произвольные Origin не разрешены.
- Проверены заголовки HTTP 200 и 304, а также отсутствие разрешающего CORS-заголовка для постороннего Origin. Конфигурация прошла `nginx -t` и применена через reload.
- Резервная копия nginx: `/root/tincraft-backups/20260826T122142Z-cache/default.conf`.
- Сервер не может заменить уже исполняемый скрипт в открытой вкладке. После исправления такую вкладку нужно обновить; при сохранении старой копии использовать `Ctrl+Shift+R`.
